# Brand and naming rules — Agentic Tree by layerPx

This document states how the product names and the interface mark of **Agentic Tree by layerPx** may be
used, and which source is the official one. It is written for everyone who reads, forks, modifies,
reviews or redistributes this work. It is not a legal opinion and it does not replace one.

The names and the mark identify the official version. That version is released by **Vitaly Averyanov**,
who also holds the copyright in the code of this repository.

- **What is covered:** the product names **Agentic Tree** and **Agentic Tree by layerPx**, and the
  layered layerPx mark shown in the plugin interface beside that name.
- **What is not covered:** the source code. The code of the rights holder in this repository is
  licensed under the **Apache License 2.0** ([LICENSE](LICENSE)) — see
  [What this document does not change](#what-this-document-does-not-change). Third-party components
  keep their own licenses ([THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)).

## The official version and the official source

The official version is the build released by Vitaly Averyanov and distributed from his own channels.
AI-generated or third-party builds are never the official version, even when they carry its name.

The official channels are:

- Repository — **live**: https://github.com/avery-tech/agentic-tree. Official releases are published on
  its Releases page; the first is
  [v0.4.2 — Public Preview](https://github.com/avery-tech/agentic-tree/releases/tag/v0.4.2), published
  2026-10-07.
- Product page — **planned**: https://layerpx.com/agentic-tree, not created yet.

An official release is an archive published through one of the official channels above — currently the
Releases page of that repository. An archive received
from anywhere else is official only as an unmodified copy of an official archive — see
[Passing on unmodified official archives](#passing-on-unmodified-official-archives). Passing an archive
on does not make anyone an official partner or representative of the product.

## Personal use and local changes

Nothing in these rules restricts personal use. You may install the product, use it, and change it for
your own purposes, including private local builds, without renaming anything and without asking for
permission. A build you do not distribute does not need its own name.

## Forks for study and fixes

An ordinary GitHub fork made to study the code, reproduce a problem or send a fix may keep the product
name and the logo files, provided that:

- the origin is stated clearly — for example in the README or the repository description — and
- nothing suggests that the fork is the official version, is supported by the rights holder, or has
  been approved by him.

A pull request or an issue in such a fork is ordinary participation. It creates no partnership and no
official status.

## Publicly distributed modified builds

A modified build that you distribute publicly as a product of its own must use its own name and its own
logo instead of the branding of the official version. Correctly stating the origin is allowed and
welcome:

> Based on Agentic Tree by layerPx

No fixed advertising line inside the interface is required, and no separate permission is needed for
that statement. What must not happen is a modified build presented under the official name or mark as
if it were the official version.

## Passing on unmodified official archives

You may pass on an unmodified official archive together with its name and branding, and state where it
came from. Doing so does not make you an official partner or representative, and it changes nothing
about the terms of the archive. Mirrors and archives of unmodified official releases are not forbidden
by this document; a mirror that changes the build is a modified build and follows the rule above.

## Reviews, articles and screenshots

Writing about the product, showing its interface, using its name and publishing screenshots are
allowed — reviews, articles, talks, comparisons and teaching material are all ordinary discussion of
the work. Material about a modified build should say that it is modified. What is not allowed is
presenting the material as an official announcement or as representation of the rights holder, or
suggesting that the rights holder reviewed or endorsed it.

## Internal identifiers and package namespaces

Technical identifiers that contain the brand word — the package name `@layerpx/harness-agent-viewer`,
the conversation view id `layerpx-tree`, the host plugin name `layerpx-agent-viewer`, the projection
name `layerpxObserver`, and local storage keys — are technical names kept for compatibility. They are
not the product's public designation: a modified build may keep them, and the build's own public name
is what identifies it to users.

A separately published third-party package needs its own name and its own namespace; it may not use the
`@layerpx` namespace.

## Notices and attribution

The required notices of the corresponding licenses must be preserved: §4 of the Apache License 2.0 for
the code of this repository ([LICENSE](LICENSE), [NOTICE](NOTICE)), and the licenses of the third-party
components actually included in a build ([THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)). Which
notice files a derived product must carry follows from the licenses and from what that product actually
contains; this document does not add a separate brand obligation on top of them.
